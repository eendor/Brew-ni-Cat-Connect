# Brew ni Cat Connect — Functional Requirements

- **Version:** 0.1 Draft
- **Date:** 2026-08-18; Phase 2 status update 2026-08-24; Phase 3 status update 2026-10-18
- **Phase:** Living requirements through Phase 3
- **Status note:** Phases 1 and 2 are merged; Phase 2 passed Renier's independent QA (PR #6). Phase 3 browser-side ordering requirements are In development (client-side) where marked, and server-side ordering remains Planned (§15). Later and conditional capabilities remain Planned or Deferred.

## 1. Requirement conventions

- **Shall** indicates mandatory behavior for the requirement's target release.
- Acceptance criteria describe observable results; detailed test data will be recorded in `test-cases.md` when implementation begins.
- Production content must be owner-approved. Unknown facts use **TODO: Confirm with Brew ni Cat owner.**
- UI fixture content must be labeled **MOCK DATA — FOR DEVELOPMENT ONLY** and isolated from production data.
- Implementation commits, pull requests, and test cases must reference relevant `FR-###` IDs.

- **FR-044 (Authenticated tracking):** Authenticated customers can view their own orders via server-side validation in `public.get_online_order(reference, null)` where `customer_id = auth.uid()`. Cross-account tracking attempts fail server-side and render a generic "Order Not Found" state without exposing order details.
- **FR-045 (Guest tracking credential):** Guests access tracking using a 43-character base64url possession token stored in the URL fragment (`#token=...`). The token is validated against `private.online_order_tokens` via SHA-256 hash. Fragments are never transmitted in HTTP headers or logged by servers.
- **FR-046 (Current status and timeline):** The order tracking component (`src/components/orders/order-status-tracker.tsx`) presents the five forward pipeline stages (`pending`, `accepted`, `preparing`, `ready`, `completed`), clearly distinguishing completed, active (`aria-current="step"`), and upcoming steps. Formatted timestamps and a chronological status history list present all recorded transitions.
- **FR-047 (Authorized Realtime updates):** The `useOrderStatus` hook (`src/lib/orders/use-order-status.ts`) subscribes to the unguessable per-order Realtime topic (`realtimeTopic`) validated via `isOrderRealtimeTopic`. When the database broadcasts `ORDER_STATUS_CHANGED_EVENT` (`status-changed`), the hook refetches the order without requiring a page reload. Terminal statuses (`isFinalOrderStatus`) automatically terminate listening.
- **FR-048 (Realtime fallback and manual refresh):** When Realtime is disconnected or unavailable, the tracker surfaces an offline status indicator and a manual "Refresh" button. A background interval polls every 30 seconds, plus visibility-change listeners refresh upon returning to the browser tab.
- **FR-049 (Exceptional and rejected states):** When an order is rejected, the tracker renders a prominent danger alert displaying the shop's rejection reason (`order.rejectionReason`) and actionable next steps (no charges made, browse alternative items, counter assistance) with a direct link back to the menu.
